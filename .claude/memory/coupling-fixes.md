# 部品どうしの依存は、原因の部品で直す

試験で、部品（スキルやエージェント）どうしの依存が見つかったら、原因の部品を直す。ほかの部品に回避の処理や決まりを足して、つじつまを合わせない（ユーザーの指摘）。

## 経緯（2026年11月、embedded-debug-loop）

部品を替える手順書どおりに部品を替える試験で、動かない所が見つかった。そのとき AI は、原因を直さずに、ほかの部品へ処理や決まりを足して動かした。

- 作業エージェントを替えたら、Web管理画面が古い作業エージェントの名前を呼んで失敗した。原因は、名前を作業フォルダの設定に保存していたこと。それを直さず、「古い名前が一覧になければ既定に戻す」処理をエクステンションに足した。
- 電源を入れ直すスキルを足したら、利用者に聞かずに電源を切った。電源を切る前に確かめるのはスキル自身の仕様なのに、作業エージェントに「使う前に聞く」決まりを足した。スキルの性質に合わせて作業エージェントの動きを変えることになり、疎結合に反する。

ユーザーは「疎結合じゃないことが原因でそこを直すべきなのに、隠して無理やり動作させる修正」と強く指摘し、ほかにも同じ直し方がないかの水平展開を求めた。独立したエージェントに監査させると、同じ種類の箇所が14か所見つかった。

## 守ること

- 直す前に、どの部品の作りが原因かを決める。その部品を直す。
- 次の直し方は、回避なので使わない。
  - 部品がない・替わった・前の版の残骸がある場合のための、例外の分岐や後始末をほかの部品に足す
  - ほかの部品の言い回しや出力の形を知って補う
  - ある部品の性質に合わせて、別の部品の決まりを足す
- 部品を替えると古くなる状態（部品の名前など）は、保存しない。
- 1か所見つかったら、同じ種類の箇所がほかにもあるとみて、独立したエージェントに全体を監査させる。

## 直す所が多ければ、先に作りを変える

部品を替える手順書を具体的に書いたら、直す所がたくさん並んだ（作業エージェントの指示書の多くの文、README、テスト、仕様書、設計書）。ユーザーは「これだけの修正がいるのは、モジュール強度が弱く、結合度が高い証拠」と指摘した。

- 手順書を書いて直す所がたくさん並んだら、手順書を整える前に、直す所が減るよう作りを変える。
- 今回は、作業エージェントの手順を「使うスキル」の表だけを見て動く形にし、仕様書・設計書から部品の名前を外した。手順は、スキルのフォルダと表の1行を直すだけになった。

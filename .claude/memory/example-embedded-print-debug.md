# 実例：組み込み機器のプリントデバッグ

## 繰り返すフェーズ

コード修正 → クロスコンパイル → デプロイ（モジュールの転送）→ デバッグ → ログ取得 → ログ検証

## そのままの AI でできること・できないこと

| フェーズ | そのままの GitHub Copilot CLI | ハーネスエンジニアリング後 |
| --- | --- | --- |
| コード修正 | できる | — |
| クロスコンパイル | できない（特殊なビルド手順を踏む必要があるため） | スキルにすれば、AI が自律的にできる |
| デプロイ | できない（組み込み機器にモジュールを転送できないため） | スキルと、その中のスクリプトなどで、AI が自律的にできる |
| デバッグ・ログ取得 | できない（コンソールからログを取れないため） | スキルと、その中のスクリプトなどで、AI が自律的にできる |
| ログ検証 | できる | — |

## 結果

- コード修正、クロスコンパイル、デプロイ、デバッグ、ログ検証をすべて AI が自律的にできるようになれば、プリントデバッグがヒューマン・イン・ザ・ループからヒューマン・オン・ザ・ループに変わり、効率が飛躍的に上がる。

## 3段階の構成（embedded-debug-loop 0.2.0、2026年11月）

利用者が決めた構成の考え方は、次の1つである。

> 組み込み機器に固有のことは、すべて2段階目の作業エージェントが吸収する。

| 段階 | 部品 | 知っていること |
| --- | --- | --- |
| 1 | 互いを知らない4つのスキル（セットアップ・クロスコンパイル・デプロイ・ログキャプチャー）。設定はスキルごとの YAML | 自分のことだけ。セットアップのスキルは、YAML のコメントだけを頼りに埋める |
| 2 | 組み込み機器の作業エージェント（`/agent` で単体でも使う） | 使うスキルの名前と役割だけ（スキルの中身は知らない） |
| 3 | 統括エージェント（`/agent` で選ぶ）・検証エージェント・Web管理画面 | 機器を一切知らない。作業エージェントには、ふつうの文（準備の確認・1回の試行）で頼む |

- Web管理画面に、機器に固有の設定の項目を置かない。代わりに、作業エージェントが返した「準備の確認」（設定の要約と足りないもの）をそのまま見せる。作業エージェントを替えれば、見える中身も替わる。
- 作業エージェントは、ask_user が使えるかと、頼みの書き出し（「これは準備の確認です」「あなたは作業役です」）で、利用者と直接話しているか、統括から頼まれたかを見分ける。
- 独立性は、書かれていないことの検査（スキルにほかのスキルやエージェントの名前がない、3段階目に機器の言葉がない、など）に加えて、差し替えて動かして確かめた。
  - スキルを別の名前のもの（scp・SSH）に替え、作業エージェントは表の名前だけを替えて、不具合を直せた。
  - プロジェクトに、同じ名前で中身の違うビルドのスキル（make を使わない、設定の項目も違う）を置くと、作業エージェントを一字も変えずに通った。
  - 作業エージェントを、別の対象向けのもの（PC の上でビルドして動かす）に替えても、統括・検証・Web管理画面を一字も変えずに PDS が回った。
- 機器は、ネットワークの名前空間と qemu で作った ARM Linux の模擬（FTP サーバー、シリアルコンソール、サム値と実行の権限を確かめる起動の仕組み）を使った。設計書：plugin-market-place の `plugins/embedded-debug-loop/docs/design/design.md`。
